# 財務與結算｜對帳管理頁企劃

## 一、頁面定位

對帳管理頁的定位，是財務與結算流程中的「核對與差異處理頁」。它的目的不是單純展示資料，也不是取代營收資料頁、收款資料頁或發票資料頁，而是提供一個能集中查看「系統應收 / 應結算資料」與「實際入帳 / 收款 / 開票結果」是否一致的工作頁面。

這頁本質上是偏作業型頁面，核心在於協助使用者快速完成以下事情：

* 核對資料是否一致
* 找出差異
* 判斷差異原因
* 確認是否已完成對帳
* 追蹤未完成與異常項目

因此，這頁的重點不在單筆深度經營，而在批次檢核、快速篩選、異常定位與明細追查。

## 二、頁面目的

本頁的主要目的如下：

1. 集中管理待對帳、已對帳、異常對帳資料
2. 協助財務人員快速比對應收資料與實際收款 / 開票 / 結算資料
3. 顯示差異金額、差異狀態與可能原因
4. 降低人工來回查找成本
5. 建立對帳處理進度與狀態追蹤機制

## 三、適用角色

本頁主要服務以下角色：

* 財務人員：進行日常對帳、異常確認、狀態更新
* 營運人員：協助追查跨部門資料差異
* 業務主管：了解特定客戶或案件是否已完成對帳
* 管理者：掌握整體對帳完成率與異常風險

## 四、設計判斷

### 4.1 是否需要詳情頁

結論：**需要詳情能力。**

原因是對帳列表只能快速告訴使用者哪一筆有差異、差多少、目前狀態是什麼，但無法完整解釋：

* 差異來自哪個欄位
* 關聯哪筆營收 / 發票 / 收款
* 是金額差異、日期差異、狀態差異，還是資料缺漏
* 歷次處理紀錄是什麼
* 目前是否有人已經介入處理

因此本頁不能只有列表，必須能查看單筆對帳明細。

### 4.2 詳情頁是否需要單獨一頁

結論：**第一版不建議做獨立詳情頁，建議採用 Drawer 或側邊詳情。**

原因如下：

* 對帳管理的主要工作流在清單，不在單筆頁
* 使用者通常會連續核對多筆資料，不適合頻繁跳頁
* 單筆詳情的主要用途是輔助判讀與處理，不是長時間深度操作
* 第一版多半以查看明細、差異原因、簡單更新狀態為主，尚不需要獨立主檔型頁面

因此本頁較適合採用：**摘要區 + 篩選區|對帳列表 + 右側詳情 Drawer**

## 五、頁面核心定位

本頁是「**對帳處理工作台**」，而不是單純的結果報表。它需要同時承接：

* 內部應收 / 營收 / 結算資料
* 外部或實際收款 / 開票 / 入帳資料
* 差異判斷結果
* 處理狀態與備註

也就是說，這頁是財務流程中的「檢查與確認中心」。

## 六、主 UIUX 建議

本頁主 UI 建議採用：**摘要卡 + 篩選區|表格列表 + Drawer 詳情**

這是最符合對帳管理目的的方式。

### 不建議的主 UI

* 不建議 Timeline：對帳不是事件脈絡閱讀場景
* 不建議 Calendar：對帳核心不是日期分布查看
* 不建議卡片流：不利於批次比對與異常掃描

### 最適合的主 UI

最適合的是 **表格型列表**，因為它最利於：

* 批次比對
* 快速篩選
* 排序找異常
* 檢視差異金額
* 查看處理狀態

## 七、頁面資訊架構

本頁建議分為四個區塊：

### 7.1 頂部摘要區

用來快速掌握整體對帳狀況，建議顯示：

* 待對帳筆數
* 已對帳筆數
* 異常筆數
* 差異總金額
* 本期對帳完成率
* 待處理高風險筆數

這區的目的不是分析，而是讓使用者一進頁就知道目前工作量與異常壓力。

### 7.2 篩選區

對帳管理非常依賴篩選，建議提供：

* 日期區間
* 客戶
* 關聯商機 / 專案
* 對帳狀態
* 差異狀態
* 收款狀態
* 開票狀態
* 負責人 / 處理人
* 關鍵字搜尋
* 是否只看異常 / 未完成

### 7.3 主列表區

本頁核心區塊，採表格形式呈現待核對資料與差異結果。

### 7.4 詳情區

點擊單筆資料後，以右側 Drawer 顯示完整對帳明細、差異比對與處理資訊。

## 八、列表頁企劃

### 8.1 列表定位

列表是對帳管理頁的主工作區，使用者在這裡應能快速完成：

* 看哪些資料還沒對帳
* 找出差異筆
* 依條件篩出要處理的資料
* 點開查看差異明細
* 更新處理狀態

### 8.2 建議欄位

主列表建議顯示以下欄位：

* 對帳編號
* 客戶名稱
* 關聯營收 / 訂單 / 發票
* 對帳日期
* 應收金額
* 實收 / 對應金額
* 差異金額
* 差異類型
* 對帳狀態
* 開票狀態
* 收款狀態
* 處理人
* 更新時間

若第一版想更精簡，可保留：

* 客戶名稱
* 對帳日期
* 應收金額
* 實收金額
* 差異金額
* 對帳狀態
* 差異類型
* 處理人

### 8.3 列表互動建議

建議支援以下互動：

* 依日期排序
* 依差異金額排序
* 依狀態篩選
* 點列開啟 Drawer 詳情
* 快速標示異常狀態
* 支援分頁

若資料量高，也可後續考慮：

* 依客戶分組
* 依月份分組
* 依狀態分組

但第一版可先不做太重。

## 九、詳情設計企劃

### 9.1 詳情呈現方式

第一版建議使用 **右側 Drawer**。

這能讓使用者在不離開清單的情況下，快速查看明細並處理多筆資料。

### 9.2 詳情用途

詳情區的目的，是讓使用者看懂「這筆為何對不上」與「目前應如何處理」，而不是承載完整大型流程。

### 9.3 詳情內容建議

詳情建議分成以下區塊：

#### 基本資訊

* 對帳編號
* 客戶名稱
* 對帳日期
* 關聯營收 / 發票 / 收款資料
* 建立時間 / 更新時間
* 處理人

#### 對帳比對資訊

* 系統應收金額
* 實際收款金額
* 差異金額
* 差異類型
* 差異說明
* 是否部分收款
* 是否跨期

#### 狀態資訊

* 對帳狀態
* 開票狀態
* 收款狀態
* 結算狀態
* 處理進度

#### 關聯資料

* 客戶
* 商機 / 專案
* 營收資料
* 發票資料
* 收款資料
* 備註 / 說明

#### 處理資訊

* 異常原因
* 處理備註
* 最近處理時間
* 最近處理人
* 是否需跨部門確認

## 十、狀態設計建議

本頁至少需要區分以下幾類狀態：

### 對帳狀態

* 待對帳
* 對帳中
* 已對帳
* 對帳異常
* 已關閉

### 差異狀態

* 無差異
* 金額差異
* 日期差異
* 資料缺漏
* 狀態不一致
* 其他異常

### 處理狀態(Tabbar)

* 全部
* 待處理
* 待處理
* 處理中
* 待確認
* 已完成

這些狀態不宜太多，第一版以實務可辨識、可篩選為優先。

## 十一、操作原則

本頁應以「核對、判讀、標記、追蹤」為主，不應以複雜編輯為主。

因此操作上建議：

* 主頁以查詢、篩選、排序為主
* 詳情以查看差異與補充說明為主
* 可允許簡單狀態更新與備註輸入
* 不建議在第一版塞入過多財務調整操作

例如合理的第一版操作有：

* 更新對帳狀態
* 填寫差異說明
* 補充內部備註
* 查看關聯資料

但不建議第一版納入：

* 複雜沖銷
* 拆帳與重分配
* 多步審批流程
* 大量批次修正核心財務資料

## 十二、第一版功能範圍建議

### 建議納入

* 對帳摘要卡
* 篩選區
* 表格列表
* 狀態標籤
* 差異金額顯示
* Drawer 詳情
* 差異說明
* 關聯資料查看
* 簡單狀態更新與備註

### 建議先不納入

* 獨立詳情頁
* 複雜批次對帳流程
* 多層審批流程
* 會計級調整功能
* 高複雜圖表分析頁

第一版的核心應是：**先把資料核對得清楚、差異找得到、處理狀態看得懂。**

## 十三、與其他頁面的分工

本頁應與其他模組清楚分工：

* 營收資料頁：查看營收與結算結果
* 收款 / 發票相關頁：查看單一財務資料來源
* 對帳管理頁：負責比對、找差異、追蹤處理進度

也就是說，對帳管理頁不是源資料主檔頁，而是跨資料來源的比對與確認頁。

## 十四、企劃結論

財務與結算的對帳管理頁，應定位為 **對帳處理工作台**。它需要單筆詳情能力，但第一版**不建議做成獨立詳情頁**，而是建議採用：

* 上方摘要卡
* 篩選區|表格列表
* 右側 Drawer 詳情
