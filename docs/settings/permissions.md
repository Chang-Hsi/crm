# 設定｜權限與角色頁企劃（重構版）

## 一、頁面定位

權限與角色頁的定位，是 CRM 設定區中的**角色治理與權限配置頁**。
它不是報表頁，也不是概覽頁，而是讓 Admin 能快速完成以下事情的管理頁：

* 篩選角色
* 快速掃描角色差異
* 查看角色權限輪廓
* 開啟抽屜查看詳情
* 新增角色
* 編輯角色
* 停用角色

依照企劃正文，系統已明確定義角色、角色權限、資料範圍與敏感操作控制，且 Admin 被定義為可管理角色與權限的主要角色，因此這頁應是**高操作密度的設定管理頁**，不是分析型頁面。

## 二、第一版資料來源策略

本頁企劃需明確註明：

**第一版直接使用完整的 mock data。**

其中以下資料需參照 `src/data/auth.js`：

* 租戶資料 `companyTenants`
* 角色資料 `roleCatalog`
* 使用者帳號 `employeeAccounts`
* tenant memberships
* primary role / roleIds
* visibleSections
* permissions
* defaultDashboardRouteName

原因是目前登入後 session 的可見模組與權限結果，就是由這些資料組出來的；設定頁若不對齊，畫面會和實際登入結果不一致。

本頁第一版雖然用 mock data，但資料結構概念仍應對齊正式企劃中的：

* `Role`
* `Permission`
* `RolePermission`
* `UserRole`
* `UserScope`

## 三、頁面目的

本頁主要目的如下：

1. 管理系統角色
2. 查看角色可見模組與權限配置
3. 管理角色資料範圍
4. 區分一般權限與敏感權限
5. 快速理解各角色差異
6. 支援角色新增、編輯、停用
7. 提供後續部門與使用者頁的角色指派基礎

## 四、這頁真正要回答的問題

這頁應幫管理者快速回答：

* 系統目前有哪些角色？
* 哪些角色是系統預設，哪些是自訂角色？
* 每個角色可見哪些模組？
* 每個角色有多少權限？
* 哪些角色有敏感操作能力？
* 哪些角色已綁定使用者？
* 哪些角色還有效、哪些即將到期或應停用？
* 某個角色若登入，系統會呈現什麼樣子？

## 五、設計方向與改版原則

這版重構的核心原則如下：

### 1. 拿掉摘要卡

理由：這頁不是經營分析頁，不需要先看 KPI。角色管理的重點是操作，不是總覽。

### 2. 主體改成篩選|列表

理由：設定頁應先支援搜尋、篩選、掃描與選取，再進入詳情。

### 3. 列表要更像「角色資產清單」

每筆角色要有清楚辨識性，而不只是文字列。

### 4. 詳情改走抽屜

理由：列表與詳情分離後，畫面更乾淨，也更符合設定頁操作節奏。

### 5. 新增與編輯共用抽屜

理由：角色頁是同一型資料的維護，新增 / 編輯不需要切頁。

### 6. Radar Chart 僅作為摘要輪廓

雷達圖可以放，但只能是角色能力輪廓摘要，**不能取代權限清單**。

## 六、主 UIUX 架構

本頁建議改成以下結構：

* 上方：頁面標題列
* 中間：篩選區|角色列表
* 右側：角色詳情抽屜
* 抽屜內：詳情 / 編輯 / 新增共用介面

這樣整體會比現在「上面卡片 + 中間列表 + 下方常駐詳情」乾淨很多。

## 七、頁面資訊架構

## 7.1 頁面標題列

建議包含：

* 頁面名稱：權限與角色
* 頁面說明：租戶級角色治理、模組可見性與資料範圍管理
* 租戶切換器
* 重新整理按鈕
* 新增角色按鈕

這裡保留租戶切換是必要的，因為目前整體登入模型本來就是 multi-tenant，而且同一使用者在不同 tenant 下角色不同。

## 7.2 篩選 / 搜尋區

這一區取代原本摘要卡，成為頁面真正起點。

建議包含：

* 關鍵字搜尋

  * 可搜尋角色名稱 / role ID / route

* 角色類型篩選(可展開收合)

  * 系統預設
  * 自訂角色
* 狀態篩選

  * 啟用中
  * 停用
  * 即將到期
  * 已過期
* 是否已綁定使用者
* 模組可見性篩選

  * 例如只看有「設定」權限的角色
* 權限級別篩選

  * 一般角色
  * 管理角色
  * 財務角色
  * 全域管理角色

## 7.3 角色列表區

這區是本頁主體，應改成更像管理清單，而不是資訊卡堆疊。

### 每列建議欄位

* 角色頭像 (請使用Element plus的icon)
* 角色名稱
* 系統預設 / 自訂標籤
* 狀態
* 到期日 / 剩餘天數（若適用）
* 可見模組數
* 權限數
* 綁定使用者數
* 操作按鈕（更多）

### 列表呈現建議

* 每列可點擊
* 點擊後開右側抽屜
* 支援 hover 狀態
* 支援選中狀態
* 可依：

  * 更新時間
  * 到期日
  * 綁定人數
  * 權限數
    排序

## 八、角色詳情抽屜設計

點擊列表後，由右側打開詳情抽屜。
抽屜是這頁真正的詳情與編輯主場。

### 抽屜用途

* 查看角色詳情
* 編輯角色
* 新增角色
* 停用角色
* 預覽角色影響

### 抽屜標題區

建議顯示：

* 角色頭像 / 縮寫
* 角色名稱
* role ID
* 狀態標籤
* 系統預設 / 自訂標籤
* 到期資訊（若有）

右上操作：

* 編輯
* 停用 / 啟用
* 儲存
* 關閉

## 九、抽屜內容架構

建議用 Tab 或分段區塊，至少包含以下內容：

### A. 基本資訊

顯示 / 編輯：

* 角色名稱
* role ID
* 角色說明
* 預設 Dashboard Route
* 是否系統預設角色
* 狀態
* 生效日
* 到期日（自訂 / 臨時角色可用）

### B. Radar Chart：角色能力輪廓

這張圖的用途定義為：

**角色能力摘要視覺化**

雷達圖六軸定義為：

* 客戶管理權限
* 商機管理權限
* 財務與結算權限
* 報表中心權限
* 系統設定權限
* 敏感操作權限

這樣可以一眼看出：

* BD 角色偏商務
* Finance 偏財務
* Manager 偏報表 / 檢視
* Admin 幾乎全滿

### Radar Chart 設計原則

* 只做摘要，不做真實規則本體
* 分數需有明確計算邏輯
* 不能取代 permissions 清單

### C. 模組可見性

顯示此角色登入後可見的 Sidebar sections。
第一版直接參照 `visibleSections`。

建議 UI：

* checklist
* module chip
* visible / hidden 雙欄展示

### D. 權限清單

顯示 permissions。
第一版直接參照 `permissions`。

建議支援：

* 依模組分組
* 依動作分組
* 原始權限字串檢視

### E. 資料範圍

顯示 / 編輯：

* self
* department
* all
* assigned_accounts

這部分在企劃正文中是正式權限模型的一部分，雖然第一版 mock 不一定完整，但一定要保留。

### F. 敏感權限

獨立顯示：

* export
* approve
* delete
* finance write
* settings edit

並標示哪些是風險操作。
企劃正文也明確要求對 delete、approve、export、financial data 做敏感控制。

### G. 綁定使用者

顯示目前有哪些人綁定這個角色：

* 使用者名稱
* email / account
* tenant
* 是否 primary role
* 是否還有其他角色聯集

資料可由 `employeeAccounts` 與 `tenantMemberships` 推算。

## 十、列表與抽屜的主要流程

### 10.1 查看角色

* 使用搜尋 / 篩選找到角色
* 點擊列表列
* 開啟詳情抽屜

### 10.2 新增角色

* 點「新增角色」
* 開空白抽屜
* 填寫基本資訊
* 設定可見模組
* 設定權限
* 設定資料範圍
* 儲存

### 10.3 編輯角色

* 點開既有角色抽屜
* 點編輯
* 修改內容
* 儲存

### 10.4 停用角色

* 點擊停用
* 確認是否仍有綁定使用者
* 若有，顯示警示
* 停用後角色不可再被新指派
