# 互動與支援｜客訴 / Issue 企劃

## 一、功能定位

客訴 / Issue 用於集中管理來自客戶、夥伴、專案執行、產品使用或日常支援過程中的問題回報、抱怨、異常事件與待處理事項。此功能屬於互動與支援模組中的核心主功能之一，但定位應偏向 **輕量、快速、可追蹤** 的問題管理頁，而不是完整客服工單系統或 ITSM 平台。

此功能的核心價值，在於把原本散落於電話、Email、聊天訊息、會議、拜訪與內部口頭交辦中的問題集中管理，並且清楚回答以下問題：

* 目前有哪些客訴或 Issue 尚未處理
* 哪些問題最急、最嚴重、最容易逾期
* 某個客戶最近是否反覆回報相同問題
* 某個商機、專案或支援案件是否正卡在某個 Issue
* 哪些 Issue 已結案，哪些還在待追蹤
* 最近團隊的問題處理壓力落在哪些類型

---

## 二、產品策略

客訴 / Issue 第一版建議刻意做簡單，聚焦在 **快速盤點、快速篩選、快速查看詳情、快速更新狀態**。不建議一開始做成複雜的多流程案件系統。

第一版建議策略如下：

* 主頁以列表為主
* 上方快速篩選改用 **Element Plus 的 Tabbar / Tabs** 形式
* 不獨立做新增頁與編輯頁
* 新增與更新可透過：

  * 其他模組轉入建立
  * 列表頁快捷建立
  * 詳情抽屜內局部編輯
* 詳情使用 **Drawer** 即可，不需要完整獨立詳情頁
* 內容紀錄以 **結構化欄位 + 簡短文字描述** 為主，不需要像會議紀錄那樣重型編輯體驗

此頁應更接近 CRM 中的 **Issue Tracker / Problem Log**，而不是文件型內容頁。

---

## 三、功能目標

客訴 / Issue 模組應支援以下目標：

* 集中管理問題回報與客訴紀錄
* 讓使用者快速辨識待處理、處理中、已結案問題
* 支援問題與客戶、商機、專案、夥伴、支援案件的關聯
* 提供簡潔的處理脈絡與責任歸屬
* 幫助團隊掌握優先級、嚴重度與逾期風險
* 作為會議紀錄、拜訪紀錄、Email / 通話後續問題沉澱的去向

---

## 四、適用情境

客訴 / Issue 常見於以下情境：

* 客戶抱怨產品或服務問題
* 專案執行中發生交付異常
* 客戶回報系統錯誤或流程卡點
* 商機推進中出現重大疑慮或反對意見
* 夥伴反映合作問題
* 支援案件需要進一步追蹤處理
* 內部跨部門待協調事項
* 同一問題需要持續跟催直到結案

---

## 五、資訊架構定位

客訴 / Issue 作為互動與支援模組下的獨立主功能頁，第一版建議包含：

* 客訴 / Issue 列表頁

同時建議在以下頁面提供 Issue 摘要區塊或建立入口：

* 客戶詳情頁
* 商機詳情頁
* 專案詳情頁

第一版不必額外拆成：

* 新增頁
* 編輯頁
* 獨立詳情頁

## 六、頁面形式設計原則

### 1. 主頁保持輕量

列表頁是主體，重點在快速看、快速篩、快速開抽屜。

### 2. 快速篩選改為 Tabs

上方快速篩選不使用一般 chip/tag 群組，改用 **Element Plus Tabs**，例如：

* 全部
* 待處理
* 處理中
* 待回覆
* 已結案
* 已逾期
* 高風險

這會比一般快速條件按鈕更穩定，也更符合此頁的工作台感。

### 3. 詳情用抽屜即可

因為客訴 / Issue 內容通常比會議紀錄、拜訪紀錄短，且更偏狀態追蹤與處理摘要，使用 Drawer 足夠。

### 4. 內容輸入不需要重型編輯器

第一版建議 **以 textarea 為主**，不需要導入 Tiptap。

## 七、Textarea 與 Tiptap 的選型建議

## 7.1 第一版建議：使用 Textarea

客訴 / Issue 的內容特性通常是：

* 問題摘要
* 問題描述
* 處理說明
* 客戶影響
* 臨時處置
* 後續追蹤

這類內容多半是 **短段落、短摘要、結構化補充說明**，通常不需要像會議紀錄那樣處理大量長文、段落層級、格式化內容或會議模板。

因此第一版建議：

* 問題描述：Textarea
* 處理紀錄：Textarea
* 備註：Textarea

## 7.2 不建議第一版使用 Tiptap 的原因

* 頁面定位本來就希望簡化
* 問題紀錄通常不需要複雜排版
* 若引入 Tiptap，會把這頁變得太重
* 會與會議紀錄、拜訪紀錄的內容層級混淆
* 第一版重點應該放在篩選、狀態與追蹤，而不是內容編排

## 7.3 後續可再升級的情況

若未來發現以下需求明顯增加，再考慮升級為富文字：

* Issue 需要長篇分析
* 需要表格或格式化處理紀錄
* 需要複雜引用與技術描述
* 需要多人協作補充大量內容

在目前企劃定位下，Textarea 更合理。

# 九、客訴 / Issue 列表頁企劃

## 9.1 頁面定位

列表頁用於集中查看所有客訴 / Issue，是此功能的主入口。頁面應偏向處理台，重點放在快速篩選、優先排序與開抽屜查看。

## 9.2 頁面目標

* 快速盤點問題總量
* 快速辨識待處理與高風險問題
* 快速切換不同狀態群組
* 快速進入抽屜查看與更新

## 9.3 頁面結構

### A. 頁首區

內容建議：

* 頁面標題：客訴 / Issue
* 頁面說明：集中管理問題回報、客訴處理與後續追蹤
* 主要操作：

  * 新增 Issue（可為簡易按鈕或快捷建立）
  * 匯出

### B. KPI 摘要區

建議簡單即可，顯示：

* Issue 總數
* 待處理數
* 處理中數
* 已逾期數
* 本週新增數

### C. 快速篩選 Tabs

建議使用 Element Plus Tabs：

* 全部
* 待處理
* 處理中
* 待回覆
* 已結案
* 已逾期
* 高嚴重度

### D. 進階篩選區

建議支援：

* 關鍵字搜尋（標題 / 描述 / 客戶）
* Issue 類型
* 負責人
* 優先級
* 嚴重度
* 關聯客戶
* 關聯商機
* 關聯專案
* 關聯夥伴
* 建立日期區間
* 是否重要

### E. 列表區

以表格為主，保持簡潔與高密度管理。

---

## 9.4 列表欄位規劃

建議主表格欄位如下：

* Issue
* 類型
* 關聯主體
* 狀態
* 優先級 / 嚴重度
* 負責人

* 合作爭議

### 狀態

* 待處理
* 處理中
* 待回覆

# 十、新增 Issue 的做法建議

## 10.1 第一版不做完整新增頁

既然希望頁面簡單，第一版建議不獨立做新增頁。

可採以下其中一種方式：

### 做法 A：列表頁上方快速建立彈窗

欄位包含：

* Issue 標題
* 類型
* 關聯主體
* 負責人
* 優先級
* 問題描述（Textarea）

### 做法 B：從其他模組快捷建立

例如從：

* 客戶頁
* 商機頁
* 專案頁
* 支援案件頁
  直接建立一筆已帶入關聯主體的 Issue

這種方式更符合此功能定位。

# 十八、風險與控管建議

* 已結案 Issue 不應無痕修改
* 狀態、負責人、優先級變更需保留歷程
* 已轉任務的 Issue 應保留關聯標記
* 逾期與高嚴重度需有清楚提示
* 第一版若採手動建立，需明確定位為問題紀錄中心，而非完整客服系統

* 使用者可快速盤點所有待處理問題
* 頁面保持簡潔，不會膨脹成複雜工單系統
