# 設定｜流程自動化頁企劃

## 一、頁面定位

流程自動化頁的定位，是 CRM 設定區中的**自動化規則管理中心**。
此頁負責管理系統內各模組的流程規則，讓原本需要人工處理的提醒、指派、狀態更新、通知與異常處理，能透過規則自動執行。

依照企劃正文，系統已明確定義自動化模組包含任務提醒、Workflow、客戶分配、KPI 警示、通知中心與 Automation Log；同時資料模型中也已定義 `WorkflowRule` 與 `AutomationLog`，並明確描述自動化流程為：事件觸發 → 規則判斷 → 執行動作 → 留下紀錄。因此本頁本質上是**規則治理與執行監控頁**，而不是一般設定表單頁。   

## 二、第一版資料來源策略

第一版直接使用完整的 mock data。
但資料概念需對齊正式模型中的：

* WorkflowRule
* AutomationLog
* Notification
* 相關模組資料（Opportunity、Contract、Settlement、Issue、Integration）

第一版即使尚未有完整後端規則引擎，也應以可展示規則、條件、動作、狀態與執行紀錄為目標，讓前端頁面與未來正式資料模型保持一致。  

## 三、頁面目的

本頁主要目的如下：

1. 建立與管理自動化規則
2. 設定規則的觸發事件、條件與執行動作
3. 控制規則的啟用 / 停用狀態
4. 查看規則最近執行情況與健康狀態
5. 查看執行失敗與異常紀錄
6. 提供可追溯的自動化執行歷程
7. 降低人工提醒、指派與狀態處理成本

## 四、這頁真正要回答的問題

本頁應幫管理者快速回答：

* 系統目前有哪些自動化規則？
* 哪些規則正在啟用？
* 規則由什麼事件觸發？
* 規則滿足哪些條件才會執行？
* 觸發後會做哪些事？
* 哪些規則最近失敗？
* 哪些異常還沒處理？
* 某條規則是否需要調整、複製或停用？

## 五、頁面設計方向

本頁採用**列表頁 + 規則編輯頁 / 抽屜 + 執行紀錄與異常處理區**的結構。

整體分為三個主要區塊：

1. **規則概覽與監控**
2. **IF-THEN 規則編輯**
3. **執行紀錄與異常排除**

此頁不以傳統單純設定表單呈現，而是兼具規則管理與執行監控的工作台頁型。

## 六、頁面資訊架構

### 6.1 規則概覽與監控

此區作為規則管理首頁，重點在快速查看規則狀態與執行健康度。

#### 頂部統計資訊

建議顯示：

* 今日執行次數
* 今日執行失敗數
* 啟用中規則數
* 待處理異常數

第一版不建議放「節省工時」類推估型指標，以避免數據口徑不明。

#### 搜尋與篩選

建議支援：

* 關鍵字搜尋（規則名稱 / 規則說明）
* 觸發模組篩選（商機、合約、分潤、對帳、整合、全域）
* 狀態篩選（啟用中 / 停用 / 異常）
* 觸發類型篩選（資料變更 / 定時觸發 / 系統異常）
* 是否最近失敗
* 是否有待處理異常

#### 規則清單欄位

建議包含：

* 規則名稱
* 觸發模組
* 觸發事件
* 作用範圍摘要
* 最後執行時間
* 最近 7 天執行次數
* 最近 7 天失敗次數
* 成功率
* 狀態切換開關
* 操作（編輯 / 複製 / 日誌）

#### 清單設計原則

* 清單中的規則應能快速看出觸發對象與執行目的
* 複製功能應保留，因為多數規則僅有條件或動作差異
* 不同模組可使用不同標籤顏色標示，例如商機、合約、財務、整合

## 七、規則編輯頁（Rule Builder）

規則編輯建議採用 **步驟引導式（Stepper）** 或 **分段卡片式配置**，讓邏輯清晰，降低規則設定複雜度。

### 第一步：基礎資訊（Basic Info）

欄位建議：

* 規則名稱
* 規則說明
* 優先等級
* 狀態（啟用 / 停用）
* 是否為系統預設規則

#### 補充說明

優先等級用於處理多條規則同時命中時的執行順序。

### 第二步：設定觸發（Trigger / WHEN）

欄位建議：

* 觸發類型

  * 資料變更
  * 定時觸發
  * 系統異常
* 觸發模組

  * 商機
  * 合約
  * 對帳
  * 分潤
  * 整合
  * Issue
* 觸發事件

  * 狀態變更
  * 到期前 N 天
  * 匯入失敗
  * 同步失敗
  * 建立 / 更新 / 關閉
* 作用範圍

  * 特定部門
  * 特定角色
  * 特定資料類型
  * 全域

#### 設計原則

Trigger 與作用範圍應分開，不應混進條件區塊。

### 第三步：設定條件（Conditions / IF）

欄位建議：

* 條件邏輯群組

  * AND
  * OR
* 條件編輯器

  * [欄位] [運算子] [值]
* 支援的條件類型

  * 狀態判斷
  * 金額門檻
  * 日期條件
  * 時間偏移
  * 優先級
  * owner / 部門
  * 是否異常
* 時間偏移條件

  * [到期日] [前 3 天]
  * [預計成交日] [後 7 天未更新]

#### 第一版限制

第一版建議只支援：

* 一層條件群組
* 不支援巢狀條件樹
* 不支援過深複合判斷

### 第四步：執行動作（Actions / THEN）

欄位建議：

* 通知

  * 選擇通知範本
  * 指定接收人
  * 支援動態標籤，如 `{商機負責人}`、`{合約 owner}`
* 任務

  * 自動建立 Task
  * 指派處理人
  * 設定期限
* 更新

  * 更新狀態
  * 更新欄位值
* 指派

  * 指派 owner
  * 指派處理人
* Log

  * 寫入自動化紀錄
* Webhook（進階預留）

#### 第一版建議必做動作

* 發通知
* 建立 Task
* 指派處理人
* 更新狀態
* 寫入 log

#### 第一版建議預留

* Webhook
* 外部系統串接型動作

## 八、執行紀錄與異常處理

此區是本頁的重要功能之一，負責讓管理者追查規則執行情況與失敗原因。

### 8.1 執行歷程

每筆紀錄建議顯示：

* 執行時間
* 規則名稱
* 觸發的資料 ID
* 相關模組
* 判斷結果
* 命中的條件摘要
* 最終執行動作
* 執行結果（成功 / 失敗）

### 8.2 異常詳情

若規則執行失敗，應顯示：

* 使用者可理解的錯誤訊息
* 技術細節展開區
* 錯誤來源類型

  * API 回傳失敗
  * 權限不足
  * 資料缺漏
  * 條件錯誤
  * 外部系統異常

第一版不建議直接將 Error Stack Trace 作為主畫面內容，而應以「清楚錯誤訊息 + 技術細節展開」方式呈現。

### 8.3 手動重試（Retry）

對於可重試型錯誤，提供：

* 重新執行按鈕
* 重試前檢查提示
* 重試結果回寫到 log

#### 補充規則

不是所有失敗都能重試。
僅限可重試型錯誤顯示 Retry。

## 九、UI / UX 補充規則

### 9.1 標籤化設計

在規則清單中，應使用不同顏色的標籤標示規則領域，例如：

* 商機
* 合約
* 財務
* 對帳
* 整合
* 通知

方便快速識別規則類型。

### 9.2 防呆機制

儲存規則時，系統應偵測並警告以下情況：

* 循環觸發
* 衝突規則
* 重複通知
* 空條件或無效動作
* 無接收人通知
* 更新動作缺少必要欄位

### 9.3 預覽測試

在規則儲存前，提供「測試運行」功能：

* 可輸入一筆測試資料 ID
* 顯示規則是否命中
* 顯示命中哪些條件
* 顯示將會執行哪些動作

### 9.4 編輯方式

第一版建議：

* 規則不複雜時，可使用側邊抽屜編輯
* 若未來規則結構擴大，再升級為獨立 Builder 頁

本頁應至少支援以下功能：

* 建立規則
* 編輯規則
* 複製規則
* 啟用 / 停用規則
* 設定觸發事件
* 設定條件邏輯
* 設定執行動作
* 查看規則列表
* 查看規則健康狀態
* 查看執行紀錄
* 查看異常詳情
* 手動重試失敗紀錄
* 規則儲存前測試運行
* 偵測循環觸發與衝突規則

## 十一、第一版建議功能範圍

### 建議納入

* 規則概覽與監控
* 搜尋與篩選
* 規則清單
* 規則新增 / 編輯
* Trigger / Condition / Action 配置
* 啟用 / 停用規則
* 複製規則
* 執行紀錄查看
* 異常詳情查看
* 可重試型錯誤的 Retry
* 規則預覽測試
* 循環觸發 / 衝突規則基本檢查

### 建議先不納入

* 太複雜的拖拉式流程圖設計器

* 完整外部 Webhook 平台管理
* 太細緻的版本歷史比較
* 過重的視覺化 builder

## 十二、頁面結論

流程自動化頁應定位為**自動化規則管理與執行監控頁**。
它的核心不是單純設定一條規則，而是同時負責：

* 管理規則
* 定義觸發與動作
* 監控規則健康狀態
* 追查執行異常
* 支援失敗補救

第一版應以「**規則概覽與監控 + IF-THEN 規則配置 + 執行紀錄與異常處理**」為主軸，先把規則建立、執行監控與異常排查三件事做穩。
