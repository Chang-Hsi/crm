# 設定｜部門與使用者頁企劃

## 一、頁面定位

部門與使用者頁的定位，是 CRM 設定區中的**組織與帳號配置頁**。
它不是一般員工清單頁，也不是權限頁的附屬頁，而是用來管理：

* 系統裡有哪些使用者
* 使用者屬於哪個租戶
* 使用者被指派了哪些角色
* 使用者可視資料範圍到哪裡
* 使用者目前實際負責哪些 account / 客戶資料
* 部門底下有哪些人，以及組織分工是否合理

依照企劃正文，權限 / 組織管理明確包含「部門組織、使用者角色指派、資料存取範圍」，而系統支援流程也明確寫到：建立角色、設定權限、指派使用者、設定資料範圍。因此這頁不是單純帳號頁，而是**角色與資料範圍真正落到人身上的配置頁**。

## 二、第一版資料來源策略

本頁企劃需明確註明：

**第一版直接使用完整的 mock data。**

但資料來源需分成兩層：

### A. 主資料來源：`src/data/auth.js`

用來提供：

* 租戶資料 `companyTenants`
* 使用者帳號 `employeeAccounts`
* tenant memberships
* primary role / roleIds
* 登入後 session 的角色與權限邏輯

目前 `auth.js` 已明確定義三個租戶、四種角色，以及三位員工帳號與其跨租戶 membership，並透過 `buildPermissionBundle()` 將多角色聯集成 `visibleSections` 與 `permissions`。這些資料會直接決定這頁第一版的使用者列表與角色配置內容。

### B. 輔助參考資料：`src/data/accounts.js`

用來提供：

* 使用者目前實際負責的 account
* `ownerUserId` 與 account 的對應關係
* 使用者受指派資料範圍的展示
* 負責 account 數、客戶類型分布、地區分布、lifecycle 分布等摘要資訊

`accounts.js` 中的 `accountList` 已有大量 `ownerUserId`，並包含 companyType、tier、lifecycleStage、region、opportunities、contracts、projects 等內容，因此很適合拿來支撐這頁中的「此使用者目前負責哪些資料」區塊。

### C. 正式模型對齊原則

雖然第一版以 mock data 為主，但資料概念仍應對齊正文中的正式模型：

* `User`
* `Department`
* `UserRole`
* `UserScope`

目前企劃正文也已將這些列為正式資料模型，且 MVP v1 就已包含 User、Department、Role、Permission、UserRole、UserScope。

## 三、頁面目的

本頁主要目的如下：

1. 管理系統中的使用者帳號
2. 管理使用者的租戶歸屬
3. 管理使用者的角色指派
4. 管理使用者的資料範圍
5. 查看使用者目前實際負責的資料
6. 幫助 Admin / Manager 理解組織配置與責任分工
7. 作為權限與角色頁之後的落地執行頁

## 四、這頁真正要回答的問題

本頁應幫管理者快速回答：

* 系統裡目前有哪些人？
* 這個人屬於哪個租戶？
* 他的 primary role 是什麼？還有哪些附加角色？
* 這個人應該看自己的資料、部門資料，還是全部資料？
* 他目前實際負責哪些 account？
* 哪些人還沒配置好角色或 scope？
* 哪些部門底下有哪些人？
* 哪些人跨租戶有不同角色與責任？

## 五、設計方向與改版原則

這頁延續你剛剛確認的新版設定頁風格，設計原則如下：

### 1. 不做摘要卡

理由：這頁是配置管理頁，不是分析頁。焦點應放在查找、掃描、配置，而不是先看 KPI。

### 2. 主體改成篩選區 + 列表

理由：管理者進頁後最常做的是找人、篩選人、點人進去改。

### 3. 列表加使用者頭像

理由：這頁比角色頁更需要「人」的辨識感。沒有頭像會太像純技術表格。

### 4. 點列表開抽屜

理由：使用者資料屬於中度複雜，適合用抽屜承接詳情與編輯，而不需要拆獨立詳情頁。

### 5. 新增與編輯共用抽屜

理由：帳號建立、角色指派、scope 配置都屬同類型維護流程，適合共用一套抽屜表單。

### 6. 部門功能先保留，但第一版不做太重

理由：正文正式模型裡 Department 很重要，但目前你現有 mock data 並沒有完整 department tree，因此第一版應先保留部門篩選與部門欄位，不建議一開始就做拖拉式組織樹編輯。

## 六、主 UIUX 架構

建議本頁採用以下結構：

* 上方：頁面標題列
* 中上：篩選 / 搜尋區
* 中間：使用者列表
* 右側：使用者詳情抽屜
* 抽屜內：查看 / 編輯 / 新增共用介面

這樣會和新版的權限與角色頁形成一致的系統語言。

## 七、頁面資訊架構

## 7.1 頁面標題列

建議包含：

* 頁面名稱：部門與使用者
* 頁面說明：租戶成員、角色指派、資料範圍與負責資料管理
* 租戶切換器
* 重新整理按鈕
* 新增使用者按鈕

由於目前帳號關係本來就是 multi-tenant，同一帳號可屬於多個租戶、不同租戶下可有不同角色，因此租戶切換必須保留在頁面主操作區。

## 7.2 篩選 / 搜尋區

建議包含：

* 關鍵字搜尋

  * 可搜尋姓名 / account / email
* 角色篩選

  * Admin / BD / Finance / Manager
* 狀態篩選

  * 啟用中 / 停用 / 待啟用
* 部門篩選
* 是否有負責 account
* 是否跨租戶
* 租戶篩選
* 資料範圍篩選

  * self / department / all / assigned_accounts

這區會比摘要卡有價值，因為它直接承接使用者管理的主要操作。

## 7.3 使用者列表區

這區是本頁主體。

### 每列建議欄位

* 使用者頭像
* 顯示名稱
* account
* email
* primary role
* 附加角色數
* 部門
* 狀態
* 所屬租戶數
* 負責 account 數
* 最近更新 / 最近登入（若第一版沒資料可先預留）
* 操作按鈕（更多）

### 使用者頭像設計建議

第一版建議：

* 使用**隨機頭像圖**或 avatar service 生成頭像
* 但需固定綁定在 user id 或 account 上，避免每次重整都變
* 若未來接真實頭像，再替換即可

也就是：

* 現階段可用 mock avatar
* 但視覺上要保持「一人一張、固定識別」

這樣對列表掃描很有幫助。

### 列表呈現建議

* 每列可點擊
* 點擊後開右側抽屜
* 支援 hover / selected 狀態
* 支援依：

  * 角色
  * 部門
  * 負責 account 數
  * 租戶數
    排序

### 列表欄位資料來源

* `displayName / account / email / tenantMemberships / primary role / roleIds`：來自 `auth.js`
* 負責 account 數與對應資料：來自 `accounts.js` 中 `ownerUserId` 的回推結果

## 八、使用者詳情抽屜設計

點擊列表後，由右側打開詳情抽屜。
抽屜是這頁真正的查看與編輯主場。

### 抽屜用途

* 查看使用者詳情
* 編輯使用者
* 新增使用者
* 啟用 / 停用使用者
* 查看角色與資料範圍
* 查看受指派資料

### 抽屜標題區

建議顯示：

* 使用者頭像
* 顯示名稱
* account
* email
* 狀態標籤
* 所屬租戶數

右上操作：

* 編輯
* 啟用 / 停用
* 儲存
* 關閉

## 九、抽屜內容架構

建議用 Tab 或分段區塊，至少包含以下內容：

### A. 基本資訊

顯示 / 編輯：

* 顯示名稱
* account
* email
* employeeId
* 狀態
* 部門
* 職稱
* 時區 / locale（若第一版要預留）
* 所屬租戶

目前 `auth.js` 已有基本帳號資訊，但部門、職稱、時區等欄位第一版要由完整 mock data 補齊。正式正文中的 User 模型本來就有 department_id、title、timezone、locale。

### B. 角色與權限

顯示：

* primary role
* roleIds
* 聯集後 visibleSections
* 聯集後 permissions
* 預設 dashboard route

目前登入規則就是依 primary role 決定首頁，依 roleIds 聯集決定 `visibleSections` 與 `permissions`，所以這區一定要完整呈現。

### C. 資料範圍

顯示 / 編輯：

* self
* department
* all
* assigned_accounts

這一區在企劃正文中是正式權限流程的一部分，也是 UserScope 模型核心，因此即使第一版只用 mock data，也一定要保留。

### D. 負責資料 / Account 摘要

這是本頁最有價值的區塊之一，建議顯示：

* 負責 account 數
* 負責客戶清單
* 客戶類型分布
* 地區分布
* lifecycle 分布
* 關聯商機數
* 關聯合約數
* 關聯專案數

因為 `accounts.js` 中的 `accountList` 已有：

* `ownerUserId`
* `companyType`
* `region`
* `lifecycleStage`
* `opportunities`
* `contracts`
* `projects`

很適合直接拿來做這塊的展示與統計。

### E. 租戶 Membership

顯示：

* 所屬 tenant
* 該 tenant 下的 primary role
* 該 tenant 下的 roleIds
* 該 tenant 下是否啟用
* 該 tenant 下的預設首頁

因為目前整個登入模型就是 multi-tenant，所以這區不能省略。

## 十、主要功能

第一版建議至少包含以下功能：

### 1. 使用者列表查看

查看全部使用者與基本配置狀態。

### 2. 搜尋 / 篩選使用者

快速依角色、租戶、狀態、是否有負責資料來找人。

### 3. 點列開抽屜查看詳情

查看單一使用者完整配置。

### 4. 新增使用者

點新增後開空白抽屜，填寫基本資料與角色配置。

### 5. 編輯使用者

可修改基本資訊、角色、scope、租戶 membership。

### 6. 啟用 / 停用使用者

在列表或抽屜中執行狀態切換。

### 7. 查看負責資料

透過 `accounts.js` 顯示此人目前實際負責的 account 與分布摘要。

## 十一、主要流程

### 11.1 查看使用者

* 進入頁面
* 用篩選 / 搜尋找人
* 點列表列
* 開啟抽屜查看詳情

### 11.2 新增使用者

* 點「新增使用者」
* 開空白抽屜
* 填寫基本資料
* 選租戶
* 指派 primary role 與附加角色
* 設定資料範圍
* 儲存

### 11.3 編輯使用者

* 點開既有使用者抽屜
* 點編輯
* 修改資料
* 儲存

### 11.4 停用使用者

* 點停用
* 若此人仍有 active account / assigned data，先顯示警示
* 停用後不可登入

## 十二、是否需要獨立詳情頁

**第一版不需要獨立詳情頁。**

原因和權限與角色頁類似：

* 這頁的核心任務是找人、掃描人、改配置
* 管理者會頻繁切換不同使用者
* 抽屜已足以承接目前資料厚度
* 目前 mock data 還不到需要完整獨立詳情頁的複雜度

未來若擴充成更完整的 IAM / HR 型後台，再考慮升級為列表頁 + 詳情頁即可。

## 十三、與其他設定頁的分工

這頁和其他設定頁應清楚分工：

* 權限與角色：定義角色能做什麼
* 部門與使用者：決定誰被套用這些角色與 scope
* 流程自動化：定義系統事件怎麼自動執行
* 系統整合：定義外部系統怎麼接
* API 管理：定義 API 存取控制
* Dashboard 設定：定義首頁與 Widget
* 參數設定：定義全域參數

也就是說，這頁是**把規則真正套到人身上的頁面**。
